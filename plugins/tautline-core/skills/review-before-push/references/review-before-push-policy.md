# Review Before Push Policy Reference

This reference keeps detailed plan review, native Stage 1 review, cross-model
implementation review, evidence, round-budget, final-preflight, and
active-supervision policy behind the concise `review-before-push` skill
entrypoint. It preserves existing behavior while making routine review guidance
easier to load.

## Review Before Push

Use this skill before pushing any non-trivial code or process change.

Do not offer required review as an optional choice. If the project adapter, handoff, source-of-truth plan, execution packet, or documented PR/issue-thread workflow pattern calls for native or cross-model review, run it unless a true blocker exists. Established means codified in a process source or explicitly generalized beyond one incident; memory, habit, Open Brain evidence, or a single prior instance is not enough to make an optional action required. Do not ask whether to run it, skip it, or decide after human reading.

Memories are never review-gate authority. If memory mentions a review requirement, use it only as evidence to locate the canonical methodology, generated adapter, source-of-truth plan, execution packet, or methodology skill. If only memory says review is required, treat that as a missing methodology/adapter control. If no authoritative rule exists, classify the gap and propose a methodology/adapter change instead of treating memory as binding.

For T2/T3 plan/spec finalization, review completion is not just a log. Run one authoring-model native/self-check before R1, then run cross-model plan review with `tautline run-plan-review --target . --plan <source-of-truth-plan> --round Rn` exactly once for that round, inspect/classify the printed log, and bind that existing trusted log with `tautline finalize-plan-review --target . --plan <source-of-truth-plan> --log <printed-log> --round Rn --verdict <clean|clean-with-deferrals|blocked> --unresolved-critical-count <n> --unresolved-p1-count <n>`. Require `tautline plan-finalization-precheck --target . --plan <source-of-truth-plan>` only where plan review exists. T0/T1 work uses brief planning and implementation gates instead of cross-model plan review. Adapter-declared review exemptions can skip plan review only through a valid `## Plan Review Exemption` section and do not skip implementation review or required gates. Rounds 1-2 are the convergence target; rounds 3-4 are self-authorized by adding `--exception-note "<reason>"` to the `run-plan-review`/`finalize-plan-review` pair; past round 4 refusal is unconditional and the remedy follows the bound evidence: finalize it only when it is clean AND still bound to the current plan, otherwise the split into smaller source-of-truth plans is mandatory. If findings do not justify another round, carry them into the implementation review focus list. Do not rerun Codex just to bind manifest evidence. Do not run `record-plan-review`, hand-edit `.plan-reviews`, disable hooks, skip required `ExitPlanMode` checks, or ask for a bypass. If plan content changed after the final allowed round, follow the successor-plan rule instead of rerunning review.

If `run-plan-review` exits `124` and prints `plan_review_stale_marker`, the review round is stale/hung: recover or rerun the configured review round, and do not classify the frozen log as review evidence.

When reviewing a plan or execution packet with three or more tasks, ask one advisory question: which tasks are file-scope-disjoint, and is a wave decomposition with a serial integration stage proposed? (Method: the execution-packet-work-loop skill's `parallel-execution.md` reference.) A missing answer is a review note for the author, never a blocking finding.

For plans that need review, the source-of-truth plan must include milestone goal, non-goals, evidence/source links, assumptions, ordered scope, dependencies, acceptance criteria, named tests/specs or validation commands, review/merge gates, risks, open decisions, and completion definition. TODO-only sections, generic placeholders, vague restatements, missing named tests/gates, missing concrete testable acceptance criteria, or missing acceptance criteria for a deliverable are stubs.

For substantial work spanning multiple milestones, multiple PRs, overnight execution, or ambiguous "build/ship/finish" requests, create/update the goal plan first and use `goal-orchestration` before milestone/PR plans.

When the next milestone or work item is identified by backlog, execution packet, delivery summary, handoff, current context, or board order, planning that item is the next safe action unless a true blocker exists. No implementation-ready plan on deck is not a stop condition. If claiming the choice cannot be resolved or no candidate exists, first inspect the adapter, backlog/source-of-truth plan path, current execution packet, latest delivery summary or continuity handoff, and relevant readiness marker; then name exactly what each artifact said and ask one exact blocker question only if the choice changes scope/risk.

T2/T3 work requires a source-of-truth plan and cross-model plan review before plan finalization. Choose the lowest defensible tier supported by evidence, or ask one exact blocker question only when the tier choice changes approved scope, risk, cost, security posture, or production behavior. Plan finalization includes asking the operator to approve implementation, invoking `ExitPlanMode`, leaving plan mode, writing an execution packet, marking ready for development, pushing a plan-only PR, or starting implementation from the plan. Recheck the review gate before plan finalization.

Plan-review P1 must name the concrete user-visible failure or expensive rework it prevents before implementation. Otherwise classify it as a non-blocking P2 note and carry it into implementation review or backlog routing.

Tool default plan locations, including home-directory plan folders, are scratch only unless the adapter explicitly makes them authoritative. Read the configured document context index before scanning source-of-truth plan directories. If read-only plan mode exits with a scratch path, migrate only T2/T3 or explicitly review-required plans into the source-of-truth path and then run the required review/precheck. `methodology-status --target . --fail-on-drift` fails when source/template paths are missing or relevant scratch plans remain. `plan-finalization-precheck` and the `Cross-Model Review Evidence` section exist only where plan review exists. Claude `ExitPlanMode` hooks are mandatory for Claude plan-mode lanes. Non-configured outside paths and resolved source-of-truth plans that fail precheck still block.

Plan-review evidence must be tracked under `<planningArtifacts.sourceOfTruth>/.plan-reviews/` and bound to the active adapter `review.codexPlanWrapper`, exact command, current plan content hash, review log hash, CLI-written run metadata hash, reviewer/model, round, verdict, unresolved Critical/P1 counts, classified findings, classifier version, and timestamp. Run metadata must say `review_scope: plan-only` and `code_diff_review: false`. Ignored logs, mtime, or chat prose are not proof. `clean` and `clean-with-deferrals` are the only finalization-eligible verdicts, and unresolved Critical/P1 counts must be zero.

## Gates

1. Confirm main is green using the project adapter command.
2. Before committing, starting/continuing a review round, pushing, or dispatching tactical subagents on an existing PR branch, run `tautline branch-liveness-check --target . --strict` or the adapter's equivalent PR-state check. Lane-local Git hooks should also block commit/push when this fails. If the current branch's PR is queued, auto-merge-enabled, merged, or closed, stop work on that branch, sync main, and continue from the source-of-truth next work item.
3. Run fast/full local gates required by the project adapter.
4. Classify implementation risk tier for the assembled diff:
   - T0: self-review plus tests/preflight; no cross-model implementation review.
   - T1: one cross-model review round.
   - T2/T3: Stage 1 native sweep plus cross-model review.
5. For T2/T3 only, run the model-native review on the exact current assembled diff:
   - Claude uses Superpowers review where available.
   - Codex uses native review, subagents, and skills.
6. For T2/T3 only, record the exhaustive Stage 1 defect-class sweep for the current assembled diff:
   - Use `tautline record-stage1-sweep --target . --native-review-note "<native review result>" --class "<defect class>: <members checked>"`.
   - Enumerate the touched classes checked, such as input bounding, output/render sinks, validation/error paths, array dimensions, deterministic fallbacks, rollout sequencing, public API leakage, atomicity/concurrency, breaking-change caller fan-out, idempotency/unique-index behavior, migration/seed ordering, generated/derived artifact freshness, and review-evidence/process integrity.
   - If a touched source file has a committed generated mirror, behavior catalog, snapshot, index, compiled doc, or other derived artifact, regenerate it or prove it is current before spending the cross-model round.
   - When the adapter declares `derivedArtifacts`, `record-stage1-sweep` blocks if a declared artifact's sources changed in the reviewed `base...HEAD` diff without the artifact being regenerated in that same diff. Use `--derived-artifact-current <path>` only for a genuine no-output-change case.
   - Fix native-review blockers before spending the cross-model round.
7. Run cross-model review before push for T1+:
   - Claude asks Codex.
   - Codex asks Claude through `tautline claude-review --target . --packet <review-packet.md>` with a packet containing exact diff, Stage 1, and validation evidence.
8. If Codex/Stage 2 reports Critical or P1/Important findings, fix them and rerun the tier-appropriate review for the changed assembled diff.
9. Fix or refute every finding open against an acceptance criterion, regardless of severity. Route every other finding to the configured backlog adapter at its honest severity, recording `ac_ref: null`, `disposition: routed` and the `routed_to` row.

   > **Scope check before disposition:** a finding whose proposed fix ADDS a module, hook, or
   > mechanism not named in the milestone plan is **presumptively out-of-AC** — record
   > `ac_ref: null` and route it at honest severity to a named backlog row carrying the finding
   > text and the reviewer's proposed fix. To treat it as AC-bearing instead, name the AC and say
   > why in the classification. Never implement new mechanism mid-loop to satisfy a finding, and
   > never downgrade severity to make routing legal.

   The `--classified-findings-json` field contract, both verbs' flag forms, and the migration
   tolerance are documented once, at `docs/reference/operations/cli-operations.md`,
   Classified-Findings Contract. `finalize-implementation-review` refuses a push-eligible
   verdict whose blocker findings do not carry `ac_ref` and `disposition`, refuses an
   AC-bearing finding recorded as routed, and refuses `--verdict clean` when anything is
   routed. `--verdict blocked` requires none of it.
10. When review is clean and final preflight is running on the frozen PR tip, use the wait for branch-isolated next-iteration planning or active polling. Do not edit the current PR diff while preflight is proving it; if preflight fails, interrupt planning and repair the current PR before push.

## Codex CLI Finding Retrieval

When Codex review is run through a CLI wrapper, the review gate includes retrieving and classifying the final assistant output. Capture the complete log, wait for terminal command status or a documented timeout, then read the final assistant review block before deciding whether the review is clean.

Codex review output must be retrieved, inspected, and classified before the
gate is clean.

Adapter-backed projects default Codex CLI fast mode to enabled. Invoke T1 implementation review through `tautline codex-run --target . --risk-tier T1 --review-round R1 -- <review.codexWrapper>`. Invoke T2/T3 implementation review through `tautline codex-run --target . --risk-tier T2 --review-round R1 --native-review-note "<native review result>" --stage1-sweep <sweep> -- <review.codexWrapper>` or the matching T3 tier. Use a framework launcher so `review.codexFastMode` is enforced. Projects may opt out only by setting `review.codexFastMode` to `false` in the adapter.

Project `review.codexWrapper` scripts should review the committed outgoing diff from the configured base branch to `HEAD`, not the whole dirty worktree. Untracked lane drafts, scratch plans, local logs, and ignored state are out of implementation-review scope unless they are intentionally added to the PR.

When adapter `review.prePushReviewEvidence` is enabled, T1+ uses `codex-run` to record Stage 2 Codex review evidence under `.ai-runs/review-evidence/` for the exact outgoing diff. T2/T3 additionally include `record-stage1-sweep` evidence. Inspect and classify the review log, then run `tautline finalize-implementation-review --target . --manifest <manifest> --verdict <clean|clean-with-deferrals|blocked> --unresolved-critical-count <n> --unresolved-p1-count <n>`. Finalization writes the tracked `<planningArtifacts.sourceOfTruth>/.impl-reviews/` ledger; include that ledger in the PR commit. Before push, `review-evidence-check --target . --strict` must prove the required tier evidence. Per-task, subagent, or milestone reviews do not satisfy this gate unless the assembled diff that is being pushed was reviewed, classified, and recorded.

Codex-to-Claude Stage 2 review is evidence-fed and non-interactive. Build a review packet with the exact diff scope, Stage 1 native review note and sweep summary when required by tier, test/validation evidence, and required file/policy excerpts, then run `tautline claude-review --target . --packet <review-packet.md>`. The launcher disables Claude tools, writes a JSON artifact, and exits 2 by default when Claude reports blockers. Do not ask Claude to discover the repo diff, run tests, use Bash/Read/Grep, or decide its own review scope from a vague prompt; that path can wedge on tool permissions or unbounded test work.

Do not infer "no findings" from a failed grep, a missing blank line, speaker tag formatting, wrapper status text, or a guessed marker such as `^codex$`. Codex output can place `codex` immediately before Markdown headings such as `## Summary`; parsers must tolerate that and fall back to manually inspecting the end of the log when extraction returns no findings.

A clean Codex review claim must cite the inspected review artifact or the explicit no-findings verdict from the final assistant output. A Codex log with unclassified assistant output is an incomplete review gate.

## Native Stage 1 Sweep

Stage 1 native review is the authoring model's exhaustive sweep of the assembled outgoing diff (`origin/main...HEAD`) for T2/T3 implementation review. Stage 2 is a confirmation pass, not a discovery loop: do the thorough work here for high-risk diffs so cross-model rounds stay few and bounded. T0/T1 work does not write this artifact by default.

For Claude-authored code, use Superpowers review plus project review agents when configured. If unavailable, run this checklist as a structured self-review and state the fallback in the sweep note.

Review the committed assembled diff from the base branch to `HEAD`, not the dirty worktree or untracked lane scratch, unless those files are explicitly part of the PR scope. Determine the base with `tautline review-evidence-check --target .`, `codex-run --scope-strict`, or `--base origin/main` so the review is scoped to `origin/main...HEAD`. Project `review.codexWrapper` scripts must review that committed outgoing diff, not the whole dirty worktree.

For each touched area, enumerate the defect classes checked and the specific members inspected: file, function, sink, path, migration, route, schema, or other concrete unit. Cover at least input bounding and validation/error paths; output/render sinks and injection surfaces; array dimensions, off-by-one, and empty/None handling; deterministic fallbacks and default branches; rollout/sequencing and migration/seed ordering; public API leakage and breaking-change caller fan-out; atomicity/concurrency and idempotency/unique-index behavior; generated/derived artifact freshness; and review-evidence/process integrity. A class is "swept" only when you name the members you actually checked, not just the class.

After two finalized clean implementation rounds with zero unresolved Critical/P1 findings, `codex-run` blocks further rounds. Stop: run `tautline finalize-implementation-review --target . --manifest <manifest> --verdict clean-with-deferrals --unresolved-critical-count 0 --unresolved-p1-count 0 --classified-findings-json <file>` and route out-of-AC findings at honest severity to named rows, or record a documented exhaustive same-class native sweep for a genuine new defect class before passing `--allow-extra-rounds` with a stated reason. When a Codex finding is a new member of a class Stage 1 already swept, re-enumerate that class exhaustively or split the work to a separate milestone/PR instead of chasing members one Codex round at a time.

Round labels such as `cap`, `final`, or `retry` do not waive Stage 1 when the changed diff is still T2/T3. After fixing Stage 2 Critical/P1 findings on a T2/T3 diff, rerun native review and record a fresh Stage 1 sweep on the updated assembled diff before the next Stage 2 round.

## Non-Negotiables

- Do not merge known Critical or P1 defects.
- A Critical/C1/P1 review finding is a repair work item, not a stopping point. If it can be fixed within approved scope, fix it and rerun the required gate/review. If it requires prerequisite PRs, dependency ordering, or a smaller safe sequence already supported by the source-of-truth plan, backlog, execution packet, or the reviewer's own recommendation, execute that sequence.
- Do not present review-blocker options as a menu when a safe recommended path exists. Ask one exact blocker question only when every viable repair path changes approved scope, risk, cost, security posture, production behavior, or standing approval.
- Review round limits bound ceremony; they are never permission to ship blockers, and they are never a reason to ask a person what to do. Every refusal on this surface prints a runnable continuation — take it.
- Implementation review budgets are risk-tiered: adapter defaults are zero Codex rounds for T0, two for T1, three for T2, and four for T3 (`review.roundBudgets`, raised in 0.36.0 — the previous shape gave T3 no more rounds than T2, and T1=1 made the mandated confirming round illegal on the first finding). Run implementation review with `codex-run --risk-tier <tier> --review-round Rn ...` so the CLI can apply the ladder. Low-risk work fixes every AC-bearing finding from its rounds and routes out-of-AC findings at honest severity instead of chasing repeated clean rounds.
- Plan-review convergence is a ladder. Rounds 1-2 are the target. Rounds 3-4 are self-authorized with a recorded `--exception-note "<reason>"` — take the round and record the reason; never ask the operator to authorize one. A confirmed structural Critical from R2 is one valid reason among others; findings that do not justify another round transfer into implementation review focus. Past round 4 the hard cap is absolute, and the remedy is chosen by whether the bound evidence can actually be finalized: finalize the existing evidence only when it is clean AND still bound to the current plan; in every other state — including evidence that is clean but STALE, which `plan-finalization-precheck` rejects — the split into smaller source-of-truth plans is mandatory. Do not spawn new source-of-truth plans merely to rebind a hash or chase a final clean round. If reviewed plan content is edited after the final allowed round, the review evidence is void for that file: create a successor source-of-truth plan carrying every unresolved finding, mark the original superseded, and review the successor within the normal cap; never retire, rewrite, or rebind existing review runs or manifests.
- Implementation-review convergence is the same ladder, shipped in 0.36.0, and **no round decision on this surface is ever an operator escalation**. The adapter `review.roundBudgets` value for the tier is the **target**, not the ceiling. The **hard cap is target + 2**. Rounds up to the target proceed. Rounds between target and cap are **self-authorized by the lane**: take them with `tautline codex-run --target . --risk-tier <tier> --review-round <Rn> --allow-extra-rounds --extra-round-reason "<reason>" --native-review-note "<what Stage 1 found>" --stage1-sweep <fresh-sweep.json> -- <wrapper>` (T2/T3; T1 omits the two Stage 1 arguments), where the reason is at least 12 characters and names the genuine new defect class (a rubber stamp is refused). Past the cap, refusal is absolute — no flag, note, or authorization raises it — and the two named exits are to resolve every Critical/P1 and bind with `tautline finalize-implementation-review --target . --manifest <manifest> --verdict clean-with-deferrals --unresolved-critical-count 0 --unresolved-p1-count 0 --classified-findings-json <file>` (routing out-of-AC findings at honest severity to named rows), or to decompose the change into smaller PRs. Do Stage 1 thoroughly so Stage 2 confirms rather than discovers. Docs-only planning artifacts take the plan-review contract and its rounds-3-4 self-authorization, not the implementation-review budget as if they were product code.
- **A confirming round on an already-remediated diff is free.** Stage 2 evidence binds to the diff hash, so fixing what a round found voids that round's evidence for the new diff; the owed re-binding round is not new inquiry and is not charged. When every recorded round for the branch binds a diff other than the current one, `codex-run` prints `codex_run_confirming_round: <prior> -> <current>` and does not spend budget. Re-record a fresh Stage 1 sweep on the remediated diff, take the round, then `finalize-implementation-review` with matching evidence. The exemption is bounded by the hard cap and fails closed whenever it cannot prove the prior rounds were voided. It is an exemption from the *budget*, never from the *round*: the confirming round is still really run. The bound is measured in **total executions against the lineage, confirming ones included — free is not unbounded.** Rounds are counted by EXECUTION per outgoing lineage (branch plus review base), never by the `--review-round` label; six executions all labelled `R1` are six rounds. The budget is compared against **charged** executions (the ones that funded new inquiry), the ceiling against **total** executions, and `codex-run` prints `codex_run_execution_count:` on every run — warning when this attempt would be the third, because three executions against one lineage means the loop is not converging. Any base change (rebase, retarget) starts a new lineage and a fresh count.
- Before 0.36.0 this ladder did not exist and the tooling genuinely blocked the owed round — the budget refusal returned before `--allow-extra-rounds` was ever read, and that flag guards a different gate (two finalized clean rounds) which a remediation loop can never accumulate. That is fixed. If round-budget tooling ever blocks a legitimate confirming round **below the hard cap** after all Critical/C1/P1 are resolved, it is a tooling defect to repair, not a license to skip evidence: file it, fix it, and until then a `--no-verify` push is a narrow, non-routine break-glass, permitted ONLY when a fresh Stage 1 sweep on the current diff records zero Critical/C1/P1, a `decision-record` names the specific tooling defect, and that defect is filed for repair. It never ships a diff with an open blocker. If the round can run, run it instead of bypassing. **At** the hard cap the refusal is intended, not a defect, and it has two runnable exits neither of which needs another Codex execution: split into smaller PRs (a new branch is a new lineage and a fresh count), or — if a recorded manifest still binds the diff being pushed — park the discretionary post-review changes and finalize on that manifest. Reaching the ceiling means the diff was still moving after the ceiling execution, which is the non-convergence the cap exists to stop, not a blocked confirmation.
- A review with no outgoing diff is refused before it can be recorded, at run, finalize, and evidence-scan time. `head_sha == base_sha`, zero diff bytes, or the empty-string digest means the review has no subject and proves nothing; the failure it closes is a void manifest matching a void state and finalizing clean. Commit the outgoing work to a feature branch first — no ledger is written and no round is spent.
- Prose-completeness and coverage-breadth findings on non-authoritative documentation default to P2 (deferral-routable) unless they create incorrect process authority.
- Starting a final, R3, `cap`, rerun, or any other named terminal/retry review round does not complete the review gate. Actively supervise it like any other background command: capture the log/PID/monitor evidence, continue parallel-safe work if available, or poll the review artifact until terminal success/failure before yielding.
- Before reporting that a Codex/Claude review is still active, verify process liveness and log freshness with `tautline monitor-status --target . --log <log> --pid <pid-if-known> --strict` or equivalent evidence. Strict monitor checks require verified PID/process identity, not only a fresh log. A stale review log is stale/hung review work, not progress; recover or rerun the configured wrapper instead of waiting.
- If a review run may outlast the current turn, arm `ScheduleWakeup` or an equivalent host self-wakeup at a concrete cadence no longer than 10 minutes. A backgrounded shell `until`, `sleep`, `wait`, `tail -F | grep`, or equivalent loop is not review supervision; no log/artifact growth for two times the cadence is stale/hung and requires kill/retry for agent-launched review work without asking.
- A live but idle review process with no log/check progress past the stale threshold is wedged. Capture the available log/tail evidence, then kill and rerun routine review rounds when safe and authorized; do not ask whether to kill and retry routine review work.
- Do not report only `R3 running`, `review running`, or `wakeup in 10 min` as the final status for a review round. The next action is active polling or parallel-safe work until the review result is consumed.
- If a review tool is down, the PR waits unless the human operator explicitly chooses an emergency path.
- Do not push assembled milestone or goal work based only on subagent-level reviews. Run the integrated Stage 1/Stage 2 review on the final diff and let `review-evidence-check --target . --strict` prove that evidence before push.
- Do not hand a changed T2/T3 diff to Codex/Stage 2 after fixing review findings until native review has reviewed that changed diff.
